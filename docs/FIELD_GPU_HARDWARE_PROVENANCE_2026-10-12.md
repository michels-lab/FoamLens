# Field 3D — Windows GPU hardware provenance (2026-10-12)

A GPU-memory result from FoamLENS should identify the **operating-system build, detected display adapters and their driver versions**, not just a number of bytes. Run:

```powershell
pwsh -File tools/capture_gpu_hardware_inventory.ps1 -OutputPath evidence/gpu-hardware.json
```

This captures Windows WMI `Win32_OperatingSystem` and `Win32_VideoController` *inventory*, sorted for reproducibility. The JSON schema is `foamlens-windows-gpu-adapter-inventory-v1`. The adapter list is a list of **detected devices**, not necessarily the device that actually rendered FoamLENS. `selectedForFoamLens` and `measuredDedicatedVramBytes` deliberately remain `null`; reported `AdapterRAM` is not copied because it is often unreliable/truncated and should not be presented as measured driver VRAM.

Capture this next to process-specific dedicated/shared GPU counter series generated by `tools/capture_gpu_memory_series.ps1`, the **exact FoamLENS source/installer SHA**, physical OpenFOAM region counts, GPU-enabled transparency status, screenshots and loaded/unloaded timestamps. On machines with several GPUs, verify the actual rendering GPU separately with validated OS/driver telemetry or WPR/WPA. Failure to query WMI returns `status: unavailable` rather than guessing.

Protected Windows CI unit tests cover multi-adapter identity/version reporting, deterministic ordering, missing hardware, and the guarantee that hardware inventory never produces a fictitious per-application VRAM number. Hosted Windows runner inventory proves the **collector can read hardware descriptors**, not that the user's actual OpenFOAM workload was tested on that hardware.

This is one independent piece of issue #40's evidence package; it does not authorize a release or close the physical VRAM/per-fragment-intersection acceptance gates.
